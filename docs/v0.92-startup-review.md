# v0.92 启动与云图解码独立审查

结论：本次修复针对已复现的真实阻塞路径，未发现尚未解决的 P1/P2；没有发现两个启动 await 移除后导致原选择被重置、旧解码覆盖新选择或像素通道变化的回归。

## 已定位的真实路径

主任务在用户授权的 Safari 原场景复现：启动长时间停留在 `Weather / mission restore · Cloud image decode`，小地图尚未绘制；当前记录为 NASA 2026-11-04 04 UTC、validity 通道、覆盖 76.19%。它进入 `Weather.texture()` 的有效性通道转换，不经过 GitHub 修复 worker。

原实现对 8K 图逐行执行 4096 次 `drawImage/getImageData`，`Weather.restore()` 等待该纹理，进而阻塞 MissionController 的恢复。即便只移除这个等待，Environment 的首次 `setQuality()` 还会等待 cloud apply，SessionMemory 随后等待 env.ready，也能继续挡住启动。因此必须同时处理两处依赖。

主任务现场证据：只把逐行读取改成 64 行条带后，解码开始约 3287ms，天气完成约 5419ms，首帧约 5433ms；此前同场景约 73 秒。最终分离版本首帧约 3533ms，随后仍显示原 NASA 记录；这部分为主任务持有的 Safari 日志与截图，本子审查未操作浏览器。

## 实现核查

- `src/weather.js:52–63`：ready 不再等待 cloud/aurora 纹理 apply，新增单次 `restoreTextures()` 在后台应用当前设置。缓存、原选择、轨道恢复及旧缓存校验保留，没有删除记录或清空选定 ID。
- `src/environment.js:195`：初始化尚未完成时不提前重复 apply cloud；初始化后的画质切换仍会按原流程更新纹理。
- `src/app.js:119`：先完成会话时间、画质、任务恢复及首次 scene update，再隐藏加载层、标记 ready，通过计时任务启动纹理恢复。没有将未完成云纹理加入另一个启动等待。
- `src/weather.js:311–324`：64 行条带保留原有效性通道计算、alpha 和方向设置。8K 高度 4096 对应 64 次 readback，辅助 RGBA 条带约 2 MiB；每条带让出事件循环，并在下一条带前检查选择是否已过期。
- 继续使用原 apply token 和串行解码队列；新选择可以使旧条带任务在下一个检查点停止，旧纹理不会替换新选择。成功前不释放当前纹理，错误不重置保存的选择。
- `src/startup-status.js` 仅更新页面加载文字和本机 console 阶段计时，没有增加外发请求。
